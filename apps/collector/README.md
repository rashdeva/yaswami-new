# collector

Ходит юзерботом по Telegram-каналам и группам (Source), каждую новую публикацию (Announcement) пропускает через предфильтр, отдаёт Gemini и, если это анонс события, записывает его в таблицу `collected_events`.

```bash
cp apps/collector/.env.example apps/collector/.env   # CHANNELS, GEMINI_API_KEY, TG_API_ID, TG_API_HASH
pnpm install
pnpm db:up && pnpm db:migrate                        # локальный Postgres с таблицами
pnpm --filter @yaswami/collector run login               # разовый вход юзербота, см. ниже
pnpm --filter @yaswami/collector start
pnpm --filter @yaswami/collector test
```

Предфильтр, извлечение через Gemini и склейка дублей живут в общем пакете `packages/extract` (`@yaswami/extract`): тем же механизмом бот разбирает анонс, присланный ему сообщением (`apps/api/src/bot.ts`).

## Юзербот

Все источники читаются через MTProto (ADR-0001). Нужен отдельный, не личный аккаунт: его могут заблокировать.

1. На my.telegram.org → API development tools создай приложение, впиши `TG_API_ID` и `TG_API_HASH` в `.env`.
2. `pnpm --filter @yaswami/collector run login` — введи телефон, код и облачный пароль; `TG_SESSION` запишется в `.env`.

Публичные каналы и группы читаются без вступления и задаются по username. Закрытый канал задаётся числовым id: вступи в него этим аккаунтом (не больше нескольких вступлений в сутки), выполни `pnpm --filter @yaswami/collector chats` и впиши id вида `-100…` в `CHANNELS` или добавь в админке, раздел «Источники». У события из закрытого канала без контакта в тексте ссылка записи ведёт на публикацию, которую видят только участники.

Одну сессию нельзя использовать в двух местах сразу: пока сборщик работает на Railway, локально с тем же `TG_SESSION` его не запускать.

### Разведка: где искать людей и кому писать первым

`src/scout.mjs` — разовый запуск руками, ничего не пишет и никуда не вступает. Он собирает публичные группы: поиск по названию (по умолчанию «Дананг», «Danang», «Хойан» и похожие), чаты из `LEAD_CHATS` и, если задан `DATABASE_URL`, обсуждения при каналах-источниках — там люди отвечают на анонсы. Читает их историю за `SCOUT_DAYS` дней (по умолчанию 30) и печатает:

- таблицу чатов: откуда найден, участники, сообщений в день, разных авторов, сколько в нём людей с интересом;
- людей с интересом к досугу, по одному на человека, лучшие первыми. Балл — сигнал × свежесть: «ищу партнёра на бачату / кто играет в покер» — 3, вопрос «куда сходить» (отбор `lead.mjs`) — 2, «только приехал, хочу познакомиться» — 1; до 3 дней ×3, до 2 недель ×2; +1 за каждое ещё одно такое сообщение. Рядом — тема по корню слова, чтобы найти событие в каталоге.

Писать первым — самым тёплым и только с конкретным событием по их теме, без ссылки в первом сообщении. Человек без username с нашего аккаунта недоступен.

```bash
pnpm --filter @yaswami/collector run login SCOUT_SESSION   # запасной аккаунт, не тот, что в TG_SESSION на Railway
pnpm --filter @yaswami/collector scout                     # или свои запросы: scout "Дананг йога" "Danang expats"
```

`src/find-sources.mjs` (`pnpm --filter @yaswami/collector find-sources [тема …]`) ищет, откуда брать события под то, что спрашивают люди. По темам (футбол, мафия, сёрф, теннис, танцы, йога, настолки, квизы и др.) он находит каналы и группы Дананга по названию и считает, сколько публикаций за месяц похожи на анонс (`looksLikeEvent`). Затем в живых чатах (`SCOUT_CHATS`) ищет сообщения со словами темы за 90 дней и собирает из них @username и ссылки t.me: так находятся инструкторы и площадки. Отметка рядом показывает, есть ли канал уже в источниках или среди организаторов (нужен `DATABASE_URL`). Ничего не пишет; источники добавляет команда.

## Данные

Таблицы описаны в `apps/api/src/db/schema.ts` и создаются миграциями API; сборщик только пишет в них (`src/store.mjs`).

`collected_events` — одно событие на строку, ключ `external_id` (`telegram:<канал>/<публикация>#<номер события в публикации>`):

- `event` (jsonb) — то, что извлёк ИИ: `title`, `description`, `starts_at` и `ends_at` (ISO 8601 с offset), `place`, `address`, `price`, `tags`, `telegram_username`, `whatsapp_phone`, `url`.
- `announcement` (jsonb) — публикация первого анонса: `id`, `url`, `published_at`, `author_username`, `text`.
- `starts_at`, `ends_at`, `telegram_username` — те же значения колонками, для выборок.
- `signup_url` — устарела: ссылку записи API собирает сам (`collectedSignupUrl` в `@yaswami/core`) и добавляет в сообщение организатору страницу события на Ясвами. Сборщик пока продолжает её заполнять.
- `claimed_event_id` — организатор подтвердил событие как своё: из него создано событие Ясвами, запись идёт через него.
- `status` — модерация: `pending` (ждёт решения в админке, раздел «Каталог»), `approved` (одобрено, ждёт обложку и ролик от иллюстратора), `published` (в ленте), `rejected` (отклонено или снято с публикации). Сборщик пишет новые события как `pending`; в ленту, на страницу события и в каталог для агентов попадает только `published`. Решение принимают в админке (очередь «По одному» в «Каталоге»: поля можно поправить и тут же одобрить) или через оператора (`admin_collected_events_update` в MCP); правка меняет `event` и колонки рядом. Повторный анонс правку не отменяет, но может дополнить пустые поля и заменить описание более длинным (`mergeEvents`). Очередь обработки и публикация — `requestNextVideo` в `apps/api/src/services.ts`.
- `views`, `reactions` — отклик на публикацию-источник: просмотры (у публикаций в группах их нет) и сумма реакций. Сборщик обновляет их каждый проход, пока событие не прошло (`refreshPosts` в `src/main.mjs`): один запрос на источник. По ним API помечает событие `popular` — отклик заметно выше, чем у остальных предстоящих событий того же источника (`popularIds` в `@yaswami/core`).

Обложка события — строка `photos` с `collected_external_id`, одна на событие. В том же проходе, что и отклик, сборщик сохраняет обложкой фото анонса (готовое превью Telegram 800 px), если обложки ещё нет. Дальше её смотрит роль-иллюстратор через MCP (`admin_covers_list`, `admin_covers_set` в `apps/api/src/mcp.ts`): оставляет фото или заменяет нарисованной; `cover_checked_at` — отметка, что обложку посмотрели. «Перерисовать» (`admin_collected_events_redo`, кнопка в карточке события в «Каталоге») удаляет обложку и сбрасывает обработку: сборщик заново берёт фото анонса, очередь перерисует обложку и ролик минут через 20.

`telegram_username` — ключ, по которому вошедшему организатору предлагается подтвердить свои события (`claimCollectedEvent` в `apps/api/src/services.ts`).

Повторный анонс того же события (`dedupe.ts` в `packages/extract`) не создаёт вторую строку, а дополняет первую и обновляет `updated_at`.

`sources` — источники (Source), которые сборщик читает каждый проход: `channel` (username без @ или `-100…`), `host_id` — организатор, из профиля которого взят канал (пусто — добавила команда), `enabled`. Откуда берутся:

- `CHANNELS` при старте: каналы, которых ещё нет, добавляются; уже известный канал не меняется, так что выключенный в админке так и остаётся выключенным;
- каналы организаторов: каждый проход сборщик добавляет до `ADOPT_PER_PASS` (5) каналов из `hosts.channel`, которых в источниках ещё нет. Немного за раз — потому что новый канал ищется по username (флудоопасно) и при первом чтении отдаёт до 100 публикаций, из них свежие — в ИИ;
- команда — в админке, раздел «Источники» (`admin_sources_create` в MCP).

Ненужный источник выключают (`enabled = false`), а не удаляют: удалённый канал организатора добавился бы снова. Канал сравнивается без учёта регистра. В канале организатора анонс часто без контакта («пишите в личку») — тогда контактом события становится сам организатор (`contactFor` в `src/host.mjs`); если организатор и есть этот канал (площадка), событие без контакта, как и раньше, не берётся.

`collector_cursors` — номер последней разобранной публикации по каждому источнику.

`hosts` — профиль Host (`src/host.mjs`), свой `id`; `telegram_id` — кто это в Telegram, `user_id` — пользователь Ясвами, если человек вошёл (иначе пусто). После каждого прохода сборщик берёт до пятнадцати контактов (`telegram_username` событий), по которым профиля ещё нет, и по каждому находит человека в Telegram: берёт его id, имя и «о себе», находит канал (личный канал профиля, иначе первая ссылка `t.me/…` или `@…` в «о себе»), читает описание канала и 30 последних публикаций и просит Gemini написать `summary` — 2–4 предложения только по сказанному в тексте. Если контактом указан канал площадки, профиль создаётся по самому каналу (`telegram_id` вида `-100…`). Если под username не человек и не канал, профиль не создаётся; такие username сборщик помнит до перезапуска. Профиль собирается один раз и не обновляется: чтобы собрать заново, удали строку.

API отдаёт профиль в `GET /collected-events/:id` массивом `hosts` (имя поля и `name` — как у Host в Luma API; `summary`, `channel_url`, `confirmed` — наши). `confirmed` — `user_id` заполнен: человек вошёл в Ясвами, и профиль привязался к нему по Telegram id (при входе или сразу при сборе, если он входил раньше).

Наружу события отдаёт API: `GET /collected-events` — предстоящие события по дате, без входа (`listCollectedEvents` в `apps/api/src/services.ts`).

## Railway

Сервис `collector` в проекте `yaswami` собирается из общего `Dockerfile`; переменная `ENTRY=apps/collector/src/main.mjs` выбирает, что запускать. Остальные переменные — как в `.env.example`, `DATABASE_URL` ссылается на адрес БД сервиса `api`. Деплой: `railway up --service collector`.

## Ограничения

- Склейка дублей — эвристика: тот же день и время плюс тот же контакт или похожее название.
- Публикации старше `MAX_AGE_DAYS` в ИИ не отправляются.
- Предфильтр (`prefilter.ts` в `packages/extract`) пропускает к ИИ только публикации с признаком даты или времени. Анонс без них («скоро открытие, ждём всех») он отсеет.
- Бесплатный уровень Gemini: Google использует запросы для улучшения своих продуктов, лимиты запросов видны в AI Studio.
- Ссылки, спрятанные под текстом, и картинки из публикаций не забираются (`image_url` всегда `null`).
- Фото сообщества: превью 320px из последних 30 публикаций канала организатора, не больше шести, в таблицу `photos` (ADR-0003). Пересматриваются раз в `PHOTOS_REFRESH_DAYS` дней (по умолчанию 7), по пять каналов за проход; фото из альбомов считаются по одному, видео не берутся.
- Канал организатора из «о себе» берётся по первому упоминанию: `@name` может оказаться ником из Instagram, под которым в Telegram чужой канал.
- Афиши не распознаются: событие, описанное только на картинке, будет пропущено.

## Аккаунты для переписки

Отдельно от читающего юзербота сборщик держит аккаунты, с которых мы пишем людям (`src/sender.mjs`, `docs/agents-inbox.md`). Они добавляются в админке `/admin` → «Аккаунты»: номер, затем код из Telegram и, если включён, пароль двухэтапной проверки. Шаги входа исполняет сборщик; сессия хранится в таблице `tg_accounts` зашифрованной ключом `ACCOUNTS_KEY`.

Сборщик — только транспорт: личные сообщения на аккаунте он передаёт в API, а из базы забирает сообщения со статусом `queued` и отправляет их. Включается переменными `ACCOUNTS_KEY`, `API_URL` и `COLLECTOR_SECRET`.

Код привязан к соединению, которое его запросило: если сборщик перезапустился между запросом кода и его вводом, код запрашивается заново.

## Вопросы «куда сходить»

Кроме источников с анонсами сборщик читает большие чаты из `LEAD_CHATS` и ищет в них людей, которые спрашивают, куда сходить (`src/lead.mjs`). Отбор — без ИИ: короткое свежее сообщение от человека с характерными словами. Найденное вместе с несколькими сообщениями перед ним уходит в API; что ответить, решает роль `hunter`, а отправляет ответ человек из админки. Если на наш ответ в чате ответили, пишущий аккаунт передаёт этот ответ в API (`src/sender.mjs`), и роль готовит следующий черновик. Анонсы из этих чатов не берутся.

В тех же чатах сборщик ищет мастеров — тех, кто сам рассказывает, что проводит: «я тренер, веду группы, записывайтесь» (`src/offers.mjs`). Отбор без ИИ: длинное сообщение хотя бы с двумя признаками самопредставления. Реклама в больших чатах часто идёт через бота чата — тогда мастер берётся по первому контакту из текста и находится в Telegram, только если ИИ подтвердил предложение. Gemini (`createOfferExtractor` в `packages/extract`) решает, предложение ли это, и извлекает Practice: название, Topic, формат, цену. Мастер ложится в `hosts` с `practices`; у кого Practice уже есть, повторную рекламу в ИИ не отправляем. В каталоге организаторов (`GET /hosts`) показываются только Practice из наших Topic.

Сборщик видит только новые сообщения. Чтобы сразу собрать мастеров из истории, есть разовый `src/find-masters.mjs`: он проходит назад на `SCOUT_DAYS` дней (по умолчанию 30) по `LEAD_CHATS` или чатам из аргументов и пишет через тот же `saveOffers`. Нужны `SCOUT_SESSION`, `DATABASE_URL` и `GEMINI_API_KEY`.

```bash
pnpm --filter @yaswami/collector find-masters                 # или свои чаты: find-masters danang_women DaNang_girls
```

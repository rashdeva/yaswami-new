# collector

Ходит юзерботом по Telegram-каналам и группам (Source), каждую новую публикацию (Announcement) пропускает через предфильтр, отдаёт Gemini и, если это анонс события, записывает его в таблицу `collected_events`.

```bash
cp apps/collector/.env.example apps/collector/.env   # CHANNELS, GEMINI_API_KEY, TG_API_ID, TG_API_HASH
pnpm install
pnpm db:up && pnpm db:migrate                        # локальный Postgres с таблицами
pnpm --filter @yaswami/collector run login               # разовый вход юзербота, см. ниже
pnpm --filter @yaswami/collector start
pnpm --filter @yaswami/collector test
```

Темы (Topic) сборщик каждый проход берёт из базы (`src/topics.mjs`): ИИ относит анонс к одной из них по её гиду или к «другому». Он же добавляет темы сам: метка, которая за 90 дней встретилась у событий без темы не меньше чем в пяти событиях у трёх организаторов, или стала заметной внутри широкой темы — от десяти событий у пяти организаторов («мафия» внутри «игр»: ИИ почти всегда находит событию какую-то тему, и без этого список не рос бы), уходит в Gemini (`createTopicProposer` в `packages/extract`), и если это вид занятий, а не свойство события, бренд или то, что мы не публикуем, — становится темой с гидом, цветом и метками; события без темы с этими метками переходят в неё, а у широкой темы новая забирает события с меткой-кандидатом, и подписанные на широкую получают и новую. Не больше одной темы за проход. `TOPICS_AUTO=0` выключает автодобавление, `TOPIC_MODEL` задаёт для него другую модель. Иконку новой теме рисует иллюстратор (очередь в API).

Предфильтр, извлечение через Gemini и склейка дублей живут в общем пакете `packages/extract` (`@yaswami/extract`): тем же механизмом бот разбирает анонс, присланный ему сообщением (`apps/api/src/bot.ts`).

## Юзербот

Все источники читаются через MTProto (ADR-0001). Нужен отдельный, не личный аккаунт: его могут заблокировать.

1. На my.telegram.org → API development tools создай приложение, впиши `TG_API_ID` и `TG_API_HASH` в `.env`.
2. `pnpm --filter @yaswami/collector run login` — введи телефон, код и облачный пароль; `TG_SESSION` запишется в `.env`.

Публичные каналы и группы читаются без вступления и задаются по username. Закрытый канал задаётся числовым id: вступи в него этим аккаунтом (не больше нескольких вступлений в сутки), выполни `pnpm --filter @yaswami/collector chats` и впиши id вида `-100…` в `CHANNELS` или добавь в админке, раздел «Источники». У события из закрытого канала без контакта в тексте ссылка записи ведёт на публикацию, которую видят только участники.

Одну сессию нельзя использовать в двух местах сразу: пока сборщик работает на Railway, локально с тем же `TG_SESSION` его не запускать.

### Разведка: где искать людей и кому писать первым

`src/scout.mjs` — разовый запуск руками, ничего не пишет и никуда не вступает. Он собирает публичные группы: поиск по названию города (`CITY_ID`, по умолчанию первый, название — из таблицы `cities`; другие написания — из «Городов» (`cities.aliases`) и `CITY_ALIASES` через запятую), чаты города (источники вида «чат города») и обсуждения при каналах-источниках города — там люди отвечают на анонсы. Нужен `DATABASE_URL`. Читает их историю за `SCOUT_DAYS` дней (по умолчанию 30) и печатает:

- таблицу чатов: откуда найден, участники, сообщений в день, разных авторов, сколько в нём людей с интересом;
- людей с интересом к досугу, по одному на человека, лучшие первыми. Балл — сигнал × свежесть: «ищу партнёра на бачату / кто играет в покер» — 3, вопрос «куда сходить» (отбор `lead.mjs`) — 2, «только приехал, хочу познакомиться» — 1; до 3 дней ×3, до 2 недель ×2; +1 за каждое ещё одно такое сообщение. Рядом — тема по корню слова, чтобы найти событие в каталоге.

Писать первым — самым тёплым и только с конкретным событием по их теме, без ссылки в первом сообщении. Человек без username с нашего аккаунта недоступен.

```bash
pnpm --filter @yaswami/collector run login SCOUT_SESSION   # запасной аккаунт, не тот, что в TG_SESSION на Railway
pnpm --filter @yaswami/collector scout                     # или свои запросы: scout "Дананг йога" "Danang expats"
```

`src/find-sources.mjs` (`pnpm --filter @yaswami/collector find-sources [тема …]`) ищет, откуда брать события под то, что спрашивают люди. По темам (футбол, мафия, сёрф, теннис, танцы, йога, настолки, квизы и др.) он находит каналы и группы города по названию (город — `CITY_ID`, его другие написания из «Городов» и `CITY_ALIASES`, как у разведки) и считает, сколько публикаций за месяц похожи на анонс (`looksLikeEvent`). Затем в живых чатах (`SCOUT_CHATS`, по умолчанию — чаты города) ищет сообщения со словами темы за 90 дней и собирает из них @username и ссылки t.me: так находятся инструкторы и площадки. Отметка рядом показывает, есть ли канал уже в источниках или среди организаторов (нужен `DATABASE_URL`). Ничего не пишет; источники добавляет команда.

Тот же поиск по названию города сборщик делает сам, в фоне (`sourceSearch` в `src/main.mjs`, таблица `source_searches`): новому городу — в первый же проход, остальным — раз в `SOURCE_SEARCH_DAYS` дней (30; `0` — только по просьбе команды: «Найти источники сейчас» в «Городах», `admin_source_searches_create` в MCP). Ищет по названию и другим написаниям города (`cities.aliases`, правятся в «Городах») — само название и по слову на тему, около 20 запросов на написание с паузой 3 с, и смотрит до 80 найденных чатов. Канал, где за месяц не меньше `SOURCE_AUTO_ADD_MIN` (3) публикаций похожи на анонс, сразу становится источником города (`0` выключает); выключенный командой канал не возвращается. Группы и остальное найденное ложатся в `results` с предложенным видом (`suggestKind`) и ждут команду в «Городах». Поиск, оборванный перезапуском, начинается заново.

## Данные

Таблицы описаны в `apps/api/src/db/schema.ts` и создаются миграциями API; сборщик только пишет в них (`src/store.mjs`). Запросы хранилища проверяет `apps/api/src/collector-store.test.ts` — на настоящей базе, вместе с остальными тестами (`pnpm test`); новый запрос добавляй и туда.

`collected_events` — одно событие на строку, ключ `external_id` (`telegram:<канал>/<публикация>#<номер события в публикации>`):

- `event` (jsonb) — то, что извлёк ИИ: `title`, `description`, `starts_at` и `ends_at` (ISO 8601 с offset), `place`, `address`, `price`, `tags`, `telegram_username`, `whatsapp_phone`, `url`.
- `announcement` (jsonb) — публикация первого анонса: `id`, `url`, `published_at`, `author_username`, `text`.
- `starts_at`, `ends_at`, `telegram_username` — те же значения колонками, для выборок.
- `signup_url` — устарела: ссылку записи API собирает сам (`collectedSignupUrl` в `@yaswami/core`) и добавляет в сообщение организатору страницу события на Ясвами. Сборщик пока продолжает её заполнять.
- `claimed_event_id` — организатор подтвердил событие как своё: из него создано событие Ясвами, запись идёт через него.
- `status` — модерация: `pending` (ждёт решения в админке, раздел «Каталог»), `approved` (одобрено, ждёт обложку и ролик от иллюстратора), `published` (в ленте), `rejected` (отклонено или снято с публикации). Сборщик пишет новые события как `pending`, а из доверенного источника — сразу `approved`: за 90 дней команда одобрила из него не меньше `AUTO_APPROVE_MIN` (5) событий и ни одного не отклонила (`trustedChannels` в `src/store.mjs`; `AUTO_APPROVE_MIN=0` выключает). Одно отклонение — и источник снова идёт через модерацию. В ленту, на страницу события и в каталог для агентов попадает только `published`. Решение принимают в админке (очередь «По одному» в «Каталоге»: поля можно поправить и тут же одобрить) или через оператора (`admin_collected_events_update` в MCP); правка меняет `event` и колонки рядом. Повторный анонс правку не отменяет, но может дополнить пустые поля и заменить описание более длинным (`mergeEvents`). Очередь обработки и публикация — `requestNextVideo` в `apps/api/src/services.ts`.
- `views`, `reactions` — отклик на публикацию-источник: просмотры (у публикаций в группах их нет) и сумма реакций. Сборщик обновляет их каждый проход, пока событие не прошло (`refreshPosts` в `src/main.mjs`): один запрос на источник. По ним API помечает событие `popular` — отклик заметно выше, чем у остальных предстоящих событий того же источника (`popularIds` в `@yaswami/core`).

Фото и видео публикации (`announcement.media`, `[{ type, url, width, height }]` в порядке альбома; фото — готовое превью Telegram 1280 px) сборщик заливает в S3-совместимый бакет с открытым чтением — Cloudflare R2 (ADR-0006), когда из публикации появляется новое событие; API отдаёт их полем `media`. Ключ файла — `telegram/<канал>/<сообщение>_<ширина>x<высота>.<расширение>`. Страница события ставит первый вертикальный ролик обложкой, остальное показывает лентой с просмотром на весь экран, одно фото не показывает (`mediaLayout` в `apps/web/src/media.ts`). Без переменных `S3_*` и `MEDIA_PUBLIC_URL` медиа не сохраняются, остальное работает как раньше. События, собранные до этого, сборщик разбирает заново (`src/refresh.mjs`): по `REFRESH_PER_PASS` (15) публикаций за проход, пока у всех предстоящих событий не появится ключ `announcement.media`. Описание заменяется полным, пустые поля дополняются. Без бакета этот проход выключен.

Обложка события — строка `photos` с `collected_external_id`, одна на событие. В том же проходе, что и отклик, сборщик сохраняет обложкой фото анонса (готовое превью Telegram 800 px), если обложки ещё нет. Дальше её смотрит роль-иллюстратор через MCP (`admin_covers_list`, `admin_covers_set` в `apps/api/src/mcp.ts`): оставляет фото или заменяет нарисованной; `cover_checked_at` — отметка, что обложку посмотрели. «Перерисовать» (`admin_collected_events_redo`, кнопка в карточке события в «Каталоге») удаляет обложку и сбрасывает обработку: сборщик заново берёт фото анонса, очередь перерисует обложку и ролик минут через 20.

`telegram_username` — ключ, по которому вошедшему организатору предлагается подтвердить свои события (`claimCollectedEvent` в `apps/api/src/services.ts`).

Повторный анонс того же события (`dedupe.ts` в `packages/extract`) не создаёт вторую строку, а дополняет первую и обновляет `updated_at`.

`sources` — источники (Source), которые сборщик читает каждый проход: `channel` (username без @ или `-100…`), `host_id` — организатор источника: сборщик ставит его, когда берёт канал из профиля, команда — в админке, в «Источниках» (пусто — не указан), `enabled`. Когда команда указывает у источника нового организатора, API стирает отметку чтения этого канала (`collector_cursors`) — сборщик перечитывает отметки каждый проход и заново разбирает последние 100 публикаций (в ИИ — только не старше `MAX_AGE_DAYS`), а если у организатора не было канала, этот канал становится его каналом. Откуда берутся:

У источника есть город (`city_id` → `cities`, раздел «Города» в админке): событие из источника получает его город, а ИИ читает анонс с названием и часовым поясом этого города. Одинаковые события склеиваются только внутри одного города. Повторный разбор уже собранных событий (дозаполнение, медиа) идёт в городе и поясе самого события.

- `CHANNELS` при старте: каналы, которых ещё нет, добавляются; уже известный канал не меняется, так что выключенный в админке так и остаётся выключенным;
- каналы организаторов: каждый проход сборщик добавляет до `ADOPT_PER_PASS` (5) каналов из `hosts.channel`, которых в источниках ещё нет. Немного за раз — потому что новый канал ищется по username (флудоопасно) и при первом чтении отдаёт до 100 публикаций, из них свежие — в ИИ;
- команда — в админке, раздел «Источники» (`admin_sources_create` в MCP).

Ненужный источник выключают (`enabled = false`), а не удаляют: удалённый канал организатора добавился бы снова. Канал, которого больше нет в Telegram (username свободен или занят не каналом, канал удалён или закрыт), сборщик выключает сам и пишет причину в `disabled_reason` — команда видит её в «Источниках»; включила снова — причина стирается (`goneReason` в `src/mtproto.mjs`). Временные сбои (флуд-лимит, сеть) источник не выключают. Канал сравнивается без учёта регистра. В канале организатора анонс часто без контакта («пишите в личку») — тогда контактом события становится сам организатор (`contactFor` в `src/host.mjs`); если организатор и есть этот канал (площадка), событие без контакта, как и раньше, не берётся.

`collector_cursors` — номер последней разобранной публикации по каждому источнику.

`tg_peers` — каналы и группы, которые читающий аккаунт уже нашёл по username: id и `access_hash` (действителен только для своего аккаунта, поэтому строки — по `account`). При старте сборщик кладёт их в сессию GramJS (`loadPeers`), после прохода дописывает новые (`newPeers`). Без этого после каждого перезапуска GramJS искал бы все источники заново через `contacts.ResolveUsername`, а этот вызов Telegram ограничивает в сутки: при сотнях источников и нескольких выкладках в день аккаунт упирается в FLOOD_WAIT. Людей не храним: их профили сборщик и так смотрит заново.

`hosts` — профиль Host (`src/host.mjs`), свой `id`; `telegram_id` — кто это в Telegram, `user_id` — пользователь Ясвами, если человек вошёл (иначе пусто). После каждого прохода сборщик берёт до пятнадцати контактов (`telegram_username` событий), по которым профиля ещё нет, и по каждому находит человека в Telegram: берёт его id, имя и «о себе», находит канал (личный канал профиля, иначе первая ссылка `t.me/…` или `@…` в «о себе»), читает описание канала и 30 последних публикаций и просит Gemini написать `summary` — 2–4 предложения только по сказанному в тексте. Если контактом указан канал площадки, профиль создаётся по самому каналу (`telegram_id` вида `-100…`). Если под username не человек и не канал, профиль не создаётся; такие username сборщик помнит до перезапуска. Раз в `PROFILE_REFRESH_DAYS` дней (по умолчанию 7) профиль пересматривается — на свободные места тех же пятнадцати за проход, начиная с ни разу не смотренных (мастера из чатов): обновляются «о себе» и канал (`profiled_at`). Имя и сводку правит команда, их сборщик не трогает; сводку пишет, только если её нет — стёрли в карточке, напишет заново. Если под username теперь другой человек или никого, профиль не меняется. Отклонённых не пересматривает. Организатора можно добавить по username в админке («Организаторы»): появляется заготовка без `telegram_id`, сборщик берёт такие первыми и заполняет на месте (`saveHost`); если под username никого нет — ставит `rejected` с пояснением в `summary` и больше не ищет, пока команда не вернёт `pending`.

API отдаёт профиль в `GET /collected-events/:id` массивом `hosts` (имя поля и `name` — как у Host в Luma API; `summary`, `channel_url`, `confirmed` — наши). `confirmed` — `user_id` заполнен: человек вошёл в Ясвами, и профиль привязался к нему по его способу входа telegram (`user_identities`, ADR-0008) — при входе или сразу при сборе, если он входил раньше.

Наружу события отдаёт API: `GET /collected-events` — предстоящие события по дате, без входа (`listCollectedEvents` в `apps/api/src/services.ts`).

## Railway

Сервис `collector` в проекте `yaswami` собирается из общего `Dockerfile`; переменная `ENTRY=apps/collector/src/main.mjs` выбирает, что запускать. Остальные переменные — как в `.env.example`, `DATABASE_URL` ссылается на адрес БД сервиса `api`. Деплой: `railway up --service collector`.

## Ограничения

- Склейка дублей — эвристика: тот же день и время плюс тот же контакт или похожее название.
- Публикации старше `MAX_AGE_DAYS` в ИИ не отправляются.
- Предфильтр (`prefilter.ts` в `packages/extract`) пропускает к ИИ только публикации с признаком даты или времени. Анонс без них («скоро открытие, ждём всех») он отсеет.
- Бесплатный уровень Gemini: Google использует запросы для улучшения своих продуктов, лимиты запросов видны в AI Studio.
- Ссылки, спрятанные под текстом, не забираются.
- Фото сообщества: превью 320px из последних 30 публикаций канала организатора, не больше шести, в таблицу `photos` (ADR-0003). Пересматриваются раз в `PHOTOS_REFRESH_DAYS` дней (по умолчанию 7), по пять каналов за проход, у всех организаторов с каналом, кроме отклонённых (не только у тех, у кого есть предстоящие события); фото из альбомов считаются по одному, видео не берутся.
- Канал организатора из «о себе» берётся по первому упоминанию: `@name` может оказаться ником из Instagram, под которым в Telegram чужой канал.
- Первое фото публикации (превью 1280 px) ИИ видит вместе с текстом и берёт сведения с афиши. Но предфильтр смотрит только текст: событие, описанное только на картинке, до ИИ не дойдёт.
- Видео публикации тяжелее 50 МБ не скачиваются. Альбом, разрезанный границей пачки из 100 публикаций, сохраняется не целиком.

## Instagram

Профили Instagram — тоже Source, ключ `instagram:<ник>` в той же таблице `sources` (ник в Instagram может совпасть с чужим каналом в Telegram). Читаются не юзерботом, а через акторы Apify без логина и без своего аккаунта (ADR-0001, `src/instagram.mjs`); без `APIFY_TOKEN` Instagram выключен.

- Откуда берутся: команда добавляет ссылкой `instagram.com/<ник>` в «Источниках»; Instagram организатора (`hosts.instagram_handle`) становится источником сам, по `ADOPT_PER_PASS` за проход; поиск источников города ищет и в Instagram — по хэштегам из названия города (`#danang`, `#danangevents`…, `cityHashtags`). Профиль, где за месяц три и больше публикаций похожи на анонс, добавляется сам, как канал.
- Как читаются: раз в `INSTAGRAM_POLL_HOURS` часов (6) один запуск `apify/instagram-scraper` на все профили, до 10 свежих публикаций с каждого; отметка источника — время последней разобранной публикации в секундах. Дальше — тот же предфильтр, ИИ и склейка дублей, что у Telegram. Фото кандидата качаются сразу (ссылки CDN Instagram живут недолго) и пережимаются в JPEG до 1280 px (`toJpeg`, sharp): Instagram отдаёт и WebP, и снимки по 2–3 МБ. Первое фото — обложка нового события (800 px, до 400 КБ), сразу при сборе: публикацию из Instagram потом не перечитываем. Ролик качается, только когда из публикации появилось новое событие, не тяжелее 50 МБ, без пережатия (Instagram уже сжал его в H.264); его размеры берутся из ответа Apify, по ним сайт ставит вертикальный ролик обложкой. Событию, собранному до обложек, обложкой становится первое фото из бакета.
- Контакт: ник профиля не считается Telegram-контактом. Событие получает `instagram_username` — «Записаться» ведёт в директ `ig.me/m/<ник>`, если нет Telegram, WhatsApp или ссылки на регистрацию. Если у источника указан организатор с Telegram, контакт — его Telegram: так аудитория из Instagram приходит в Telegram.
- Деньги: Apify берёт за каждую публикацию (~$2.3 за тысячу); каждый запуск ограничен `APIFY_MAX_USD` и числом записей. Отклик (лайки, просмотры роликов) пишется один раз при сборе и потом не обновляется.

## Аккаунты для переписки

Отдельно от читающего юзербота сборщик держит аккаунты, с которых мы пишем людям (`src/sender.mjs`, `docs/agents-inbox.md`). Они добавляются в админке `/admin` → «Аккаунты»: номер, затем код из Telegram и, если включён, пароль двухэтапной проверки. Шаги входа исполняет сборщик; сессия хранится в таблице `tg_accounts` зашифрованной ключом `ACCOUNTS_KEY`.

Сборщик — только транспорт: личные сообщения на аккаунте он передаёт в API, а из базы забирает сообщения со статусом `queued` и отправляет их. Включается переменными `ACCOUNTS_KEY`, `API_URL` и `COLLECTOR_SECRET`.

Код привязан к соединению, которое его запросило: если сборщик перезапустился между запросом кода и его вводом, код запрашивается заново.

## Вопросы «куда сходить»

Кроме источников с анонсами сборщик читает большие чаты города — источники вида «чат города» (`kind = leads`) и ищет в них людей с интересом к досугу (`src/lead.mjs`). Отбор — без ИИ, по трём сигналам: `seek` — ищет компанию или партнёра на занятие («ищу партнёра на бачату», «кто играет в теннис»); `ask` — спрашивает, куда сходить; `newcomer` — только приехал, хочет знакомиться. Найденное вместе с временем сообщения и несколькими сообщениями перед ним уходит в API; что ответить, решает роль `hunter`, а отправляет ответ человек из админки. Сообщение не старше двух часов (`LEAD_REPLY_HOURS`) получает черновик ответа в чат, более старое — черновик в личку. Если на наш ответ ответили, пишущий аккаунт передаёт этот ответ в API (`src/sender.mjs`), и роль готовит следующий черновик. Анонсы из этих чатов не берутся.

Ещё два сигнала — не про досуг: `service` — человек просит посоветовать мастера или услугу («посоветуйте массажиста», «ищу тренера по теннису»; список услуг — `SERVICE` в `lead.mjs`); `job` — сам ищет работу («ищу работу поваром»; резюме бывает длинным, поэтому до 3000 знаков). `job` берётся и из чатов о работе (`kind = jobs`), остальные сигналы — только из чатов города. API передаёт охотнику город чата, и каталог он смотрит в этом городе. Тому, кто ищет работу, охотник подбирает вакансию и пишет в личку.

Сборщик видит только новые сообщения. Людей из истории разово отправляет `src/backfill-leads.mjs`: проходит назад на `SCOUT_DAYS` дней (по умолчанию 7) по чатам города из источников (вид `leads`) или чатам из аргументов, по одному сообщению на человека, тёплые первыми, не больше `LEADS_LIMIT` (60), с паузой `LEADS_PAUSE_MS` между ними. Нужны `SCOUT_SESSION`, `API_URL`, `COLLECTOR_SECRET` и `DATABASE_URL`.

```bash
pnpm --filter @yaswami/collector backfill-leads              # или свои чаты: backfill-leads DaNang_girls danangchat_ask
```

В тех же чатах сборщик ищет мастеров — тех, кто сам рассказывает, что проводит: «я тренер, веду группы, записывайтесь» (`src/offers.mjs`). Отбор без ИИ: длинное сообщение хотя бы с двумя признаками самопредставления. Реклама в больших чатах часто идёт через бота чата — тогда мастер берётся по первому контакту из текста и находится в Telegram, только если ИИ подтвердил предложение. Gemini (`createOfferExtractor` в `packages/extract`) решает, предложение ли это, и извлекает Practice: название, Topic, формат, цену. Мастер ложится в `hosts` с `practices` и ссылкой на сообщение (`offer_url`); каждая Practice получает статус `pending`. У кого Practice уже есть, повторную рекламу в ИИ не отправляем. Во вкладку «Услуги» (`GET /hosts`) Practice попадает только после «Одобрить» в админке («Каталог» → «Услуги») и лишь из наших Topic. Организатор с опубликованными событиями виден и без услуг; «Отклонить» в карточке мастера убирает из каталога его целиком.

В тех же чатах сборщик ищет людей под Запросы организаторов (`host_searches`): подтверждённый организатор пишет в мини-приложении («Мои» → «Поиск людей»), кого ищет — «ищут массаж, болит спина». Новому или переписанному Запросу Gemini (`createSearchMatcher` в `packages/extract`, `search.ts`) один раз выводит корни ключевых слов. Дальше отбор без ИИ (`pickSearchCandidates` в `src/lead.mjs`): короткое сообщение от человека, не от самого организатора, со словом Запроса; кандидата проверяет Gemini — ищет ли автор это сам или, наоборот, предлагает. Подошедшее ложится Находкой в `host_search_matches`, организатор видит её в мини-приложении и пишет человеку сам: мы найденным людям не пишем. Каждый кандидат — запрос к ИИ с паузой `LLM_PAUSE_MS`.

Сборщик видит только новые сообщения. Чтобы сразу собрать мастеров из истории, есть разовый `src/find-masters.mjs`: он проходит назад на `SCOUT_DAYS` дней (по умолчанию 30) по чатам города из источников или чатам из аргументов и пишет через тот же `saveOffers`; мастер получает город чата. Нужны `SCOUT_SESSION`, `DATABASE_URL` и `GEMINI_API_KEY`.

```bash
pnpm --filter @yaswami/collector find-masters                 # или свои чаты: find-masters danang_women DaNang_girls
```

## Вакансии

Вакансии (Job) сборщик ищет в чатах о работе и в чатах города (`src/jobs.mjs`). Чаты — источники вида `jobs` и `leads` (админка, «Источники»: вид и город); `JOB_CHATS` и `LEAD_CHATS` (username без @ через запятую) лишь добавляются туда при старте сборщика, в первый город. Чат, который уже есть в источниках с другим видом, сборщик не переделывает, а пишет в журнал предупреждение — вид меняет команда. Чат о работе даёт одни вакансии: ни мастеров, ни вопросов «куда сходить», ни Находок из него не берём (`pickFromChat` в `src/lead.mjs`). Адрес API для вакансий не нужен.

Отбор без ИИ (`looksLikeJob`): сообщение от 60 до 3000 знаков хотя бы с одним признаком — «вакансия», «требуется / ищем / нужен … <должность>», «в команду», «график работы», «з/п», «зарплата», hiring; резюме («ищу работу», «рассмотрю предложения») отсекаются сразу. Gemini (`createJobExtractor` в `packages/extract`, `job.ts`) решает, вакансия ли это именно в нашем городе — резюме, другой город и удалённая работа не проходят — и вынимает `title`, `employer`, `description`, `pay` и контакт. Контакт — `@username` из текста, иначе автор сообщения; без username вакансия не сохраняется. Вакансия ложится в `jobs` со статусом `pending` и ждёт решения команды в «Каталоге».

Повтор — тот же текст в том же городе без учёта регистра и пробелов (`text_hash`): в ИИ не идёт и вторую строку не создаёт, а сдвигает `posted_at`; решение команды не меняется. Гость видит вакансию `JOB_TTL_DAYS` (30) дней от `posted_at`. Объявления, которые ИИ отверг, сборщик помнит до перезапуска и повторно не отправляет. Вакансия и мастер получают город чата; его название ИИ видит при разборе вакансии.

Сборщик видит только новые сообщения. Вакансии из истории разово собирает `src/backfill-jobs.mjs`: проходит назад на `SCOUT_DAYS` дней (по умолчанию 30) по чатам о работе и чатам города из источников или чатам из аргументов и пишет через тот же `saveJobs`. Нужны `SCOUT_SESSION`, `DATABASE_URL` и `GEMINI_API_KEY`.

```bash
pnpm --filter @yaswami/collector backfill-jobs                # или свои чаты: backfill-jobs danang_rabota jobinvietnam
```

# План реализации

Основание: `docs/research/telegram-widgets-rsvp.md`, `docs/architecture-draft.md`, прототипы в `prototypes/`.

## Допущения (поменять здесь, если не так)

1. Работаем в этом репозитории; каталог практик — прошлая версия идеи. `CONTEXT.md` и ADR 0001 переписываются/помечаются `superseded` на шаге 1.
2. Запускаемся на сообщении с кнопками, не дожидаясь виджетов в группах. Виджет в личном чате с ботом — с первого дня.
3. Список гостей виден всем, у кого есть сообщение; в карточке — только имена, без фамилий и username.
4. Ответы гостя: **Пойду / Не пойду / Думаю** (`going` / `declined` / `maybe`).
5. Типы билетов — как в Luma, но бесплатные: гость записывается сразу, без оплаты и возвратов. Купонов нет. Подробности — `docs/architecture-draft.md`, «Типы билетов».

## Что нужно от человека

- Токен бота лежит в `.env` (`BOT_TOKEN`, файл в `.gitignore`). Для проверки групп и пересылок нужен ещё бот на тестовом сервере.
- В @BotFather: включить инлайн-режим и мини-приложение — к шагу 4.
- Решения по допущениям 1–3.

## Сначала всё локально

До первого деплоя ничего внешнего, кроме самого Telegram:

- бот получает обновления через `getUpdates` (long polling), вебхук не нужен;
- API — Hono на Node, БД — Postgres с PostGIS в Docker (`docker compose up`), через Drizzle;
- мини-приложение — `vite dev`; чтобы открыть его внутри Telegram, нужен HTTPS-туннель (cloudflared или ngrok) — только на шаге 4;
- Railway появляется отдельным шагом после шага 5, код при этом не меняется: та же версия Postgres и те же расширения, что локально.

**Готово, когда:** ядро покрыто тестами и не импортирует ничего про Telegram и БД.

### 3. API и бот (`apps/api`, `packages/telegram`)

- [x] `docker-compose.yml` с Postgres + PostGIS (тот же образ, что будет на Railway).
- [ ] Hono на Node, Postgres + Drizzle: таблицы `users`, `events`, `ticket_types`, `guests`, `shares`, миграции. _Таблицы и первая миграция готовы (`apps/api/src/db/schema.ts`, `pnpm db:up && pnpm db:migrate`); Hono ещё нет._
- [x] Сверка таблиц с ядром: источник правды — схемы zod из `packages/core`; рядом с таблицами Drizzle проверка типов (тип строки таблицы = тип из ядра), при расхождении `typecheck` падает.
- [ ] Проверка `initData` мини-приложения → `User`.
- [ ] REST: `POST /events` (создаёт и тип билета по умолчанию), `GET /events/:id`, `GET /events` (мои), `PATCH /events/:id`, `POST /events/:id/rsvp` (с необязательным `ticket_type_id`), `POST /events/:id/share` (готовит сообщение, возвращает id для `shareMessage`).
- [ ] REST типов билетов: `POST /events/:id/ticket-types`, `PATCH /ticket-types/:id`, `DELETE /ticket-types/:id`.
- [ ] Обновления через long polling (тот же обработчик потом станет вебхуком): `callback_query` (`rsvp:<id>:<g|n|m>`), `widget_query`, `/start <event>`.

- [ ] Обновление витрин после RSVP: все `shares` события; для общего виджета — не чаще раза в секунду, изменения склеиваются.

**Готово, когда:** событие создаётся запросом, нажатие кнопки в чате меняет список и текст сообщения у всех.

# Фото храним в Postgres, только превью

> Обложки событий с 25.11.2026 — в R2: ADR-0011. Фото сообщества Host с 28.11.2026 — тоже в R2 (ADR-0006). Здесь остаются аватары.

Фото пользователей (аватар из Telegram, показывается в списке гостей) лежат в таблице `photos`, в колонке `bytea`. API отдаёт их по адресу `/api/photos/<id>` с `Cache-Control: immutable`: строка фото не меняется, новое фото — новая строка с новым id.

Почему не иначе:

- **Диск контейнера** стирается при каждой выкладке.
- **Том Railway** привязан к одному сервису и одному писателю, а пишут двое: сборщик (обложки собранных событий) и API (аватары, обложки).
- **S3 / Storage Buckets** — отдельный сервис, ключи и presigned-ссылки ради десятков мегабайт. База уже есть, и сборщик, и API к ней подключены, фото попадают в общий бэкап. Это заменяет пункт про Buckets из ADR-0002, пока верны условия ниже.

## Consequences

- Аватары — JPEG 320px, 10–30 КБ, не больше 200 КБ. Оригиналы не храним.
- Превью Telegram не сжимаем: он уже хранит уменьшенные копии. API берёт аватар размером 320px через бота (`getUserProfilePhotos`), одним путём для мини-приложения, бота и входа с сайта.
- Нарисованные иллюстратором обложки приходят PNG на 1–3 МБ, поэтому при сохранении (`optimizeImage` в `photos.ts`, через `sharp`) их перекодируют в JPEG не шире 1000px, качество 78 — 60–150 КБ. Уже лежащие тяжёлые фото сжимает разовый `node apps/api/src/optimize-photos.ts`.
- У пользователя одно фото, у события — одна обложка.
- Запросы списков не выбирают колонку `data`: байты читает только `/api/photos/<id>`.

## Пересмотрено 2026-11-28: фото сообщества Host — в бакете

Фото сообщества открываются на весь экран, а 320px там мылится. Их перенесли в бакет R2 вместе со следующим готовым размером Telegram — 800px, 50–150 КБ (ADR-0006): ровно повод из пункта ниже. Таблица `photos` больше не знает о Host; адреса лежат в `hosts.photos`.

## Когда пересматривать

Переезжать в Storage Buckets, если появится хотя бы одно из двух: нужны большие картинки или оригиналы (сотни килобайт на фото), либо фото становится десятки тысяч — таблица в гигабайты раздувает бэкапы, а отдача байтов занимает соединения с базой. Переезд простой: адрес фото уже отдельный, меняется только то, куда он ведёт.

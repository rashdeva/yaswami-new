# Фото храним в Postgres, только превью

Фото пользователей (аватар из Telegram, показывается в списке гостей) и фото сообщества Host (последние картинки из его канала) лежат в таблице `photos`, в колонке `bytea`. API отдаёт их по адресу `/api/photos/<id>` с `Cache-Control: immutable`: строка фото не меняется, новое фото — новая строка с новым id.

Почему не иначе:

- **Диск контейнера** стирается при каждой выкладке.
- **Том Railway** привязан к одному сервису и одному писателю, а пишут двое: сборщик (фото сообщества) и API (аватары).
- **S3 / Storage Buckets** — отдельный сервис, ключи и presigned-ссылки ради десятков мегабайт. База уже есть, и сборщик, и API к ней подключены, фото попадают в общий бэкап. Это заменяет пункт про Buckets из ADR-0002, пока верны условия ниже.

## Consequences

- В базе только превью: JPEG с длинной стороной 320px, 10–30 КБ, не больше 200 КБ. Оригиналы не храним.
- Сами картинки не сжимаем, и библиотеки для этого нет: Telegram уже хранит уменьшенные копии. Сборщик скачивает готовый размер `m` (320px) через MTProto, API — аватар `t.me/i/userpic/320/…` из init-data. Следующий готовый размер Telegram — 800px (`x`), промежуточных нет.
- У пользователя одно фото, у Host — не больше шести; лишние удаляются при обновлении. Фото сообщества сборщик пересматривает раз в неделю.
- Запросы списков не выбирают колонку `data`: байты читает только `/api/photos/<id>`.

## Когда пересматривать

Переезжать в Storage Buckets, если появится хотя бы одно из двух: нужны большие картинки или оригиналы (сотни килобайт на фото), либо фото становится десятки тысяч — таблица в гигабайты раздувает бэкапы, а отдача байтов занимает соединения с базой. Переезд простой: адрес фото уже отдельный, меняется только то, куда он ведёт.

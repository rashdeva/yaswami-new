# Telegram — один из способов входа, а не id пользователя

Заменяет решение ADR-0007 о знаке id и о том, что Telegram не пишется в `user_identities`. Остальное в ADR-0007 — вход через Apple и Google, удаление аккаунта — в силе.

До этого id пользователя (`users.id`) совпадал с его Telegram id, а Telegram был особым случаем. В ADR-0007 вошедшим через Apple и Google дали отрицательные id: «есть ли Telegram» решал знак числа. В таком виде каждый новый способ входа и каждая будущая склейка аккаунтов упирались бы в то, что один поставщик и есть первичный ключ. Telegram id расходился по коду как «id пользователя», и наоборот.

## Решение

- **`users.id` — наш непрозрачный случайный id**, 16 цифр: 10^15 плюс 52 случайных бита из `gen_random_uuid()` (default колонки). Не подряд — чтобы по id нельзя было перебрать пользователей или узнать, сколько их, и не Telegram id — чтобы id не выдавал Telegram. Миграция `20261124115558_random_user_ids` (24.11.2026) переписала старые id — равные Telegram id и −1, −2, −3 из временной последовательности — на случайные: внешние ключи на `users.id` — `ON UPDATE cascade`, журнал команды (`admin_actions`) и авторы `admin:<id>` в переписке переписаны там же. Тип остался `bigint`: значения влезают в `Number.MAX_SAFE_INTEGER`.
- **Все способы входа — строки `user_identities (provider, subject, user_id)`:** `telegram` (subject — Telegram id строкой), `apple`, `google`. Миграция `20261123132534_telegram_identities` записала строку `telegram` всем прежним пользователям. Пара `(provider, subject)` уникальна: один Telegram — у одного пользователя. Пара `(user_id, provider)` тоже уникальна: у пользователя не больше одного способа каждого поставщика.
- **Переход между id — только через функции в `auth.ts`:**
  - `telegramIdOf` / `telegramIdsOf` — пользователь → куда писать в Telegram (`null` — некуда);
  - `userIdByTelegram` / `usersByTelegram` — Telegram id из апдейта, переписки или сборщика → пользователь;
  - `signInWith` — любой вход: найти по способу входа или завести пользователя; `upsertUser` — вход через Telegram поверх него.
- **Где Telegram id, а где id пользователя:**
  - Telegram id: `chat_id` в Bot API, `conversations.peer_id`, `hosts.telegram_id`, авторы объявлений, `ADMIN_IDS`, `SUPPORT_USER_IDS`, аргумент `pnpm api:token`;
  - id пользователя: все `user_id` в базе и API, `as_user_id` в MCP, автор `admin:<id>` в переписке, `-r<id>` в ссылках, id в PostHog, адреса админки.

## Почему не иначе

- **Колонка `users.telegram_id`.** Удобнее для запросов, но Telegram снова стал бы особым, а следующий способ входа (телефон, почта) поднял бы тот же вопрос. Одна таблица для всех поставщиков — и вход, и привязка устроены одинаково.
- **Оставить старые id и выдавать новые подряд.** Так сначала и сделали: старые id выдавали Telegram id (например, `user_id` организатора в ответе API), новые −1, −2, … перебирались и показывали число пользователей. Переписали, пока пользователей меньше двадцати. Цена — история в PostHog и ссылки `-r<id>`, разосланные до 24.11.2026, остались со старыми id.
- **uuid или строка вроде `usr-…` в Luma.** Честнее, но меняет тип `user_id` в каждой таблице, схемах core, MCP и клиентах. Случайного `bigint` хватает, чтобы id не перебирался.

## Последствия

- Тесты не могут полагаться на совпадение: `uid(<telegram id>)` в `api.test.ts` даёт id пользователя, а у любого пользователя id случайный и с Telegram id не совпадает.
- `isAdmin` асинхронный: он сверяет Telegram id пользователя с `ADMIN_IDS`.
- Привязать Telegram к пользователю Apple или Google — значит вставить строку `('telegram', id)` к его `user_id`; данные никуда не переезжают. Экрана для этого пока нет (ponytail в `web-login.ts`). Слить два уже наполненных аккаунта можно только руками.

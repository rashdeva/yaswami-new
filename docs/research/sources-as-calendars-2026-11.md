# Source как календарь: сверка с Luma и с данными, ноябрь 2026

Дата сверки: 2026-11-25. Вопрос: у одной «вывески» бывает и Telegram-канал, и Instagram-профиль, а Source у нас —
одна платформа (`sources.channel`, Instagram — `instagram:<ник>`). Связать их сейчас можно только через Host
(`sources.host_id`), но многие Source — не Host, а афиши. Похожи ли наши Source на Calendar в Luma?

## Как это устроено в Luma

По `docs/reference/luma/openapi.json` (скачан 2026-11-12):

- **Каждое событие управляется календарём**: «Every event and API key on Luma is managed by a Luma Calendar»
  (`GET /v1/calendars/events/list`).
- **У календаря два вида событий** — поле `access`: `manage` (свои: календарь их ведёт) и `view` (чужие, только
  перечислены: «listed on the Calendar but managed elsewhere»). Чужое событие попадает в календарь через
  `POST /v1/calendars/events/add`, в том числе событие с внешней платформы (`platform: "external"`, `url`),
  и проходит модерацию: `submission_mode: auto | pending`, `.../events/approve`, `.../events/reject`.
- **Личный или общий**: `AdminCalendar.is_personal` — личный календарь человека отличается от календаря сообщества.
- **Соцсети у календаря, а не у события**: `instagram_handle`, `twitter_handle`, `youtube_handle`, `tiktok_handle`,
  `linkedin_handle`, `website`. Telegram среди них нет.
- Ещё у календаря: `name`, `slug`, `avatar_url`, `description`, `location` (город), `launch_status`
  (`launched | coming-soon | archived` — это имя мы уже взяли для города), подписчики
  (вебхук `calendar.person.subscribed`).

Получается, «вывеска с Telegram и Instagram» в Luma — это один Calendar с несколькими handle, а «афиша чужих
событий» — Calendar, где большинство событий `access: view`.

## Что у нас в данных

Источник — прод, публичный API: `GET /api/collected-events?city_id=…`, `GET /api/collected-events/:id`,
`GET /api/hosts?city_id=…`. Вошли только опубликованные предстоящие события: Дананг — 68, Нячанг — 45.
Канал события взят из его `id` (`<канал>-<публикация>-<n>`), контакт для записи — из `signup_url`.

Признак: сколько разных контактов для записи у событий одного Source.

| Source | Событий | Разных контактов | Тем | На что похож |
|---|---|---|---|---|
| danang_tysa | 13 | 10 | 7 | афиша |
| dancedananganons | 9 | 5 | 1 | сообщество одной темы (танцы, разные преподаватели) |
| danangevent | 6 | 4 | 3 | афиша |
| danangpals | 6 | 4 | 3 | афиша |
| ncndldanang | 6 | 1 | 1 | канал Host |
| icebath_ceremoni | 5 | 1 | 4 | канал Host |
| electrosyndicate_vn, party_danang, businessbreakfastdanang | 2–3 | 2 | 1–2 | бренд или площадка: свои события, несколько ведущих |
| остальные 13 в Дананге | 1–2 | 1 | 1 | канал Host |
| eventnhatrang | 26 | 17 | 10 | афиша |
| afisha_nhatrang | 9 | 9 | 8 | афиша |
| daovibe | 6 | 1 | 2 | канал Host |

Выводы:

1. **Три вида Source, а не два.** Канал Host (один контакт), канал площадки, бренда или сообщества (свои
   события, несколько ведущих), афиша (чужие события, много контактов и тем).
2. **Афиши дают большую долю витрины**: в Дананге 34 из 68 событий (50%) из четырёх афиш, в Нячанге — 37 из 45
   (82%) из трёх.
3. **Контакт почти никогда не равен каналу**: ни у одного Source username канала не совпал с контактом для записи
   (у канала Host контакт — его личный аккаунт). Поэтому «свой» канал отличаем по тому, что контакт один, а не по
   совпадению имён.
4. **Связка Telegram + Instagram уже есть у Host**: в Дананге у 15 из 74 Host есть и канал, и `instagram_handle`;
   в Нячанге Instagram пока ни у кого нет. У афиш такой связки нет совсем: им некуда её записать.
5. **У событий из Instagram канал теряется**: их `id` — `ig.<код публикации>`, и по публичным данным не понять,
   из какого Source событие. Сопоставлять Instagram-источники с Telegram-источниками придётся по таблице `sources`.

## Что это значит для модели

Наши Source и Host вместе уже частично повторяют Calendar из Luma, но разрезаны по-другому:

| Luma | У нас сейчас | Чего не хватает |
|---|---|---|
| Calendar | Source (одна платформа) + иногда Host | вывески, объединяющей Telegram и Instagram |
| `is_personal` | Source с `host_id` | признака у Source без Host |
| `access: manage` / `view` | не различаем | понимания, своё событие у Source или он его перечисляет |
| `instagram_handle` у календаря | `hosts.instagram_handle` | места для handle у афиши |
| `events/add` + approve | сборщик + модерация собранных | — (уже есть) |

Вариант, который вытекает из сверки: **Calendar как отдельная сущность**. Source ссылается на календарь, у календаря
есть Telegram и Instagram, название, аватар и, если это канал Host, его Host. Событие календаря-афиши — `view`, его
организатор берётся из контакта, а у календаря Host — `manage`. Вид календаря можно предлагать автоматически по числу
разных контактов (выше), а подтверждает его команда.

Решение — ADR-0011: календари введены для всех источников, организатор перенесён на календарь, вид подсказывается по числу контактов и тем. Людям календари пока не показываются.

Открытые вопросы:

- Показывать ли календари людям (страница афиши и подписка на неё, как в Luma) или они нужны только для сбора и админки.
- Канал площадки (вид 2): это календарь с несколькими Host или Host-площадка. В Luma — календарь, у события — свои `hosts`.
- Прошедшие события и выключенные Source в сверку не вошли: публичный API отдаёт только предстоящие. Чтобы
  досчитать долю афиш точнее, нужен `/admin/collected-events` и таблица `sources` целиком.

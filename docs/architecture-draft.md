# Архитектура приложения событий — черновик

Статус: **черновик для обсуждения**, не ADR. Основание — `docs/research/telegram-widgets-rsvp.md`.

## Главный принцип

**RSVP-ядро не знает, как событие показано.** Виджет, сообщение с кнопками и страница в мини-приложении — три «витрины» одного и того же события. Так мы запускаемся на том, что работает сегодня, и включаем виджеты в группах в день, когда Telegram откроет их в продакшене, не переписывая ничего, кроме витрины.

```
            ┌────────────── Telegram ──────────────┐
 Мини-       │  виджет        сообщение    кнопка-   │
 приложение  │  (widget_query) с кнопками   ссылка   │
     │       │      │        (callback)       │     │
     │       └──────┼────────────┼────────────┼─────┘
     ▼              ▼            ▼            ▼
  REST API ──►  ┌───────────────────────────────┐  ◄── MCP (/mcp, токен)
  (initData)    │  RSVP-ядро: Event, Guest,      │      Claude, Codex
                │  правила (лимит, лист ожидания)│
                └──────────────┬────────────────┘
                               ▼
                 витрины обновляются: editSharedWidgetData,
                 editMessageText, push в мини-приложение
```

## Стек

Один язык — TypeScript — на всём пути, одна схема данных на фронт и бэк: источник правды — схемы zod в `packages/core`, типы выводятся из них. Таблицы Drizzle описаны отдельно и сверяются с ядром при компиляции.

| Слой | Выбор | Почему |
|---|---|---|
| Фронт (мини-приложение) | React + Vite, `telegram-web-app.js` | Самый распространённый набор, легко найти людей и примеры |
| Бэк | Hono на Node | Маленький, читается как Express |
| Бот | Вебхук в том же бэке, вызовы Bot API через `fetch` | Библиотеки ещё не поддерживают 10.4; тонкая типизированная обёртка над нужными методами. Позже — grammY |
| БД | Postgres + PostGIS через Drizzle | Впереди гео-поиск и очереди; образ с PostGIS выбран до первой миграции (ADR 0002) |
| Очереди | pgmq в той же БД | Напоминания, обновление витрин; отдельный брокер не нужен (ADR 0002) |
| Хостинг | Railway: API, воркер, Postgres, статика мини-приложения | Одна платформа (ADR 0002). App Sleeping выключен: на `widget_query` надо ответить за 15 с |
| MCP | Официальный SDK, Streamable HTTP на `/mcp` в том же бэке | Четвёртый вход рядом с мини-приложением и ботом: те же операции и те же схемы, отдельного сервиса нет |
| Виджет | Чистый HTML/CSS/JS + скрипт сборки с проверкой размера | Любой фреймворк съест лимит 4 КБ |

**Про ADR 0002 (Railway).** Остаётся в силе (решение от 2026-11-11): нужны гео, очереди и одна платформа. Из него берём образ Postgres `postgresql-extensions` с PostGIS и pgmq. MTProto-воркер и Buckets из того ADR относятся к каталогу и здесь пока не нужны.

## Структура репозитория

```
apps/
  web/        мини-приложение (React)
  api/        Hono: REST для мини-приложения + MCP + вебхук бота
packages/
  core/       Event, Guest, правила RSVP, схемы (zod). Без Telegram и без БД
  widget/     исходник виджета, сборка, проверка 4 КБ, стенд
  telegram/   обёртка Bot API: sendWidget, editSharedWidgetData, answerWidgetQuery, …
prototypes/   то, что сделано сейчас; уедет в packages/widget и apps/web
```

## Модель данных

Имена полей — как в Luma API (сверено с документацией 2026-11-11): `name`, `start_at`, `end_at`, `timezone`, `user_id`, `max_capacity`, `geo_address_json`, `meeting_url`, у гостя — `approval_status`, `registered_at`. Без оплаты, купонов и календарей.

```
User        id (telegram id), first_name, username, lang, timezone
Event       id (короткий slug), user_id → User (организатор), kind (f|b|w|c|s|o), name, description?,
            start_at (UTC), end_at?, timezone, geo_address_json {address}?, meeting_url?, max_capacity?,
            allow_plus_one, status (draft|published|cancelled), widget_id?, rev, created_at
TicketType  id, event_id, name (≤ 30), description?, max_capacity?, is_hidden,
            price_text?, position
Guest       (event_id, user_id) — первичный ключ; approval_status (approved|maybe|declined|waitlist),
            event_ticket_type_id → TicketType, plus_ones, registered_at
Share       id, event_id, kind (widget|inline_message), chat_id?, message_id?, inline_message_id?
```

Чего в Luma нет и что остаётся нашим: `kind` (шаблон), `status`, `allow_plus_one` и `plus_ones`, `widget_id`, `rev`, `price_text`, `position` и ответ гостя `maybe` («Думаю»). Ответ «Пойду» хранится как `approved`. Адреса запросов пока свои (`POST /events`, `POST /events/:id/rsvp`), а не как в Luma (`/v1/events/create`).

Профиль организатора собранного события отдаётся массивом `hosts` с полем `name`, как Host в Luma. Описания и ссылок у человека в Luma нет, поэтому `summary`, `channel_url` и `confirmed` — наши; `id`, `email` и `avatar_url` из Luma Host не отдаём.

### Типы билетов

Имена полей — как в Luma API (`name`, `description`, `max_capacity`, `is_hidden`). Билет бесплатный: гость записывается сразу, система деньги не трогает.

- У события всегда есть хотя бы один тип. При создании события заводится тип по умолчанию; последний оставшийся и последний видимый тип удалить нельзя (правило Luma).
- `max_capacity` типа — лимит мест этого типа; `Event.max_capacity` — общий лимит события. Запись проходит, если не превышен ни один.
- `price_text` — подпись вроде «30 лари, оплата на месте». Заменяет поля Luma `type` / `cents` / `currency`, которые нужны только для оплаты.
- `is_hidden` — тип не виден в общем списке; в v1 назначается только организатором.
- Отличие от Luma: у гостя один билет (`event_ticket_type_id`), а не массив `event_tickets`. «+1» остаётся числом `plus_ones`.
- Один видимый тип — гость отвечает кнопкой в чате, как раньше. Несколько — кнопка «Пойду» открывает мини-приложение с выбором типа: в виджет и в три кнопки выбор не помещается.
- Не берём сейчас: `require_approval`, окно продаж (`valid_start_at` / `valid_end_at`), `max_per_guest`, `tint_color`, платные типы, купоны.

- `Event.rev` растёт при каждом изменении и попадает в состояние виджета — клиент отбрасывает устаревшее.
- `Share` нужен, чтобы обновлять сообщения-витрины. Для общего виджета достаточно `widget_id`, для сообщений с кнопками нужен каждый `inline_message_id`.
- `Guest` с составным ключом: один человек — один ответ на событие, из какого бы чата он ни нажал.

## Протокол виджета

Общее состояние (`public_data`, ≤ 1024 байт):

```json
{"r":12,"k":"s","t":"Футбол 5×5","d":1794000000,"p":"Стадион «Локомотив»","c":10,"n":[9,2],"g":["Миша","Дато","Лёша","Ника","Саша"],"u":"yaswamibot/app?startapp=e_2a9c"}
```

`r` ревизия · `k` шаблон · `t` название · `d` время (unix) · `p` место · `c` лимит · `n` [пойдут, думают] · `g` первые имена · `m` 1, если видимых типов билетов несколько (тогда «Пойду» открывает мини-приложение) · `u` ссылка на событие.

Бюджет: название ≤ 60 символов, место ≤ 80, пять имён ≤ 16 символов — в кириллице это около 600 байт, запас есть.

| | Формат |
|---|---|
| Запрос виджета | `rsvp:g` · `rsvp:m` · `rsvp:n` (6 из 64 байт) |
| Ответ бота | `{"s":"g","r":13,"n":[10,2],"g":[…]}` — свой статус и свежие счётчики, чтобы не ждать опроса |
| Свой ответ | хранится в `localStorage` сообщения и подтверждается ответом бота |

Обработка запроса: проверить данные → применить правило (лимит → лист ожидания) → ответить `answerWidgetQuery` → поставить обновление состояния в очередь. Запись в общий виджет — не чаще раза в секунду, изменения склеиваются.

## Этапы

| Этап | Что делаем | Результат |
|---|---|---|
| 0. Проверка (1–2 дня) | Бот на тестовом сервере: общий виджет в группе, инлайн, пересылка. В продакшене — подготовленное сообщение с callback-кнопками | Ответы на открытые вопросы из исследования |
| 1. MVP | Мини-приложение: создать по шаблону → поделиться сообщением с кнопками. Виджет в личном чате с ботом: «моя запись» | Работает у всех уже сейчас |
| 2. Виджеты в чатах | Витрина «общий виджет» — как только Telegram включит группы и инлайн | Целевой опыт |
| 3. Удержание | Напоминания, «добавить в календарь», лист ожидания, «+1», со-организаторы | Причина вернуться |
| 4. Деньги | Платные типы билетов, купоны, депозиты через кошелёк в виджете | Модель заработка |
